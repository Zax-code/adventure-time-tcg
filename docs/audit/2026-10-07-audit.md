# Audit du code — 7 octobre 2026

Périmètre : `apps/phoenix`, `apps/mobile`, `apps/web`, `packages/*`, hygiène du repo.
Méthode : quatre passes parallèles (une par zone) puis re-vérification manuelle des points « high ».
Rien n'a été modifié. Chaque point indique **[C]** confirmé en lisant le chemin de code de bout en bout, ou **[P]** plausible (impact déduit, non mesuré).

Baseline : `mix compile --warnings-as-errors` propre, 144/144 routes ↔ actions, `npm run typecheck` propre (web + mobile), aucune dépendance mix inutilisée, aucun index manquant sur les chemins chauds.

## 1. Les dix points à traiter en priorité

| # | Zone | Sévérité | Résumé |
|---|------|----------|--------|
| P1 | Phoenix | **High** | Le worker leaderboard re-calcule chaque minute tous les snapshots de toutes les journées depuis le lancement (croissance sans borne). |
| P2 | Phoenix | **High** | Chaque requête authentifiée coûte 4 requêtes SQL rien que pour `auth_user` ; `/me` en fait 8. |
| P3 | Phoenix | **High** | L'état PvP est rejoué depuis les événements plusieurs fois par requête, et pour tous les matchs vivants sur `list_spectatable`. |

## 2. Phoenix (`apps/phoenix`)

### 2.1 Ce qui n'a pas de sens / bugs

**A1 [C] High — Scoring ranké sur un temps client, module d'attestation inutilisé.**
- `quests_controller.ex:92` lit `elapsedMs` du body ; `quests.ex:531` le stocke ; `leaderboards/scoring.ex:344-350` calcule `anchor_points * (anchor_ms / elapsed_ms)^exponent`.
- `leaderboards/ranked_sessions.ex` (`start_daily_numbers`, `settle_daily_numbers`, `FOR UPDATE`, nonce, deadline) n'a aucun appelant dans `lib/` ; seul `test/.../quest_results_test.exs:107,115` l'utilise. `quest_results.ex:263` force `ranked_session_id: nil`.
- `POST /quests/daily-numbers/ranked-start` (`quests.ex:493`) est un alias no-op de `daily_numbers_state`. Le mobile ne l'appelle plus ; seul le web l'appelle encore (voir web A3).
- Fix : soit brancher `RankedSessions` (ranked-start → `start_daily_numbers`, submit → `settle_daily_numbers`, elapsed calculé côté serveur), soit supprimer module + table `ranked_sessions` + colonne `ranked_session_id` pour que le contrat n'implique plus une attestation serveur.

**A2 [C] Medium — `perform_action` / `end_turn` sans verrou de ligne.**
- `pvp.ex:396-402` : `Repo.get(Match)` sans lock, `reconstruct_state`, `guard_your_turn` hors transaction. `next_match_seq` (`:1117-1126`) fait `max(seq)+1` puis `insert!`.
- Deux requêtes concurrentes du même joueur passent le guard ; la seconde explose sur l'index unique `(match_id, seq)` → 500 au lieu d'un 409.
- Fix : `Repo.one(from m in Match, where: m.id == ^id, lock: "FOR UPDATE")` dans la transaction avant le guard, et rescue de la contrainte unique en `{:error, :conflict}`.

**A3 [C] Medium — Deux tables d'économie dust/craft.**
- `catalog.ex:13-20` (`@dust_sacrifice_by_rarity`, `@craft_cost_multiplier`) alimente `/rarities` ; `inventory.ex:16-17,35-40` est une seconde copie qui est celle réellement facturée par `craft_card` / `recycle_card`.
- Fix : `Catalog` délègue à `Inventory.dust_sacrifice_value/1` et `dust_craft_cost/1`.

**A4 [C] Medium — Des endpoints GET écrivent en base à chaque appel.**
- `GET /quests` → `list_quests_for_user` (`quests.ex:269-306`) fait `materialize_daily_quests` (upsert), `sync_steps_quest` (`update_all`), `QuestResults.sync_safely`. Idem `perfect_timing_state` et `daily_numbers_state`.
- `Pvp.list_matches` / `list_history` / `list_spectatable` / `get_spectate` lancent des sweeps d'expiration ; `list_spectatable` et `get_spectate` le font **globalement** (`expire_due_in_progress_matches(nil)`), chaque match dû étant rejoué.
- Fix : déplacer matérialisation et expiration dans les crons Oban existants (`LeaderboardLifecycleWorker`, `ExpirePendingInviteWorker`) ; au minimum scoper les sweeps à l'utilisateur.

**A5 [C] Low — `RateLimit.Store.prune_expired/1`** (`plugs/rate_limit/store.ex:14`) scanne/supprime toute la table ETS avant chaque `check_and_increment`. Fix : prune sur timer.

### 2.3 Performance

**C1 [C] High — `LeaderboardLifecycleWorker` : cron `* * * * *` (`config.exs:110`) → `Lifecycle.tick/1` (`lifecycle.ex:35-55`).**
- `competition_dates/2` (`:83-95`) renvoie **toutes** les dates distinctes depuis le lancement (15 août 2026, donc ~53 jours aujourd'hui, et ça grandit).
- Pour chacune : `ensure_day_period` + `finalize_day_if_due` (`:174-207`) qui, même pour une journée déjà `closed`, ouvre une transaction, prend un lock par board, puis `build_all_snapshots` (`:232-247`) → pour chacun des 11 boards, `Projection.rows` (chargement complet des résultats + ranking Elixir ; les boards dérivés récursent sur 2 à 5 boards) + `persist_snapshot` pour constater que la signature n'a pas changé. `refresh_week` fait pareil par semaine + `award_week`.
- `QuestResults.reconcile_open_week` (`quest_results.ex:104-124`) charge en plus tous les `step_snapshots` de la semaine et appelle `sync_safely` par ligne, chaque minute.
- Fix sans régression : court-circuiter `finalize_day_if_due` / `refresh_week` quand `period.status in [:closed, :corrected]` et qu'aucun résultat accepté n'a bougé depuis `snapshot.source_cutoff` ; restreindre `competition_dates` aux périodes ouvertes/closing + hier/aujourd'hui ; limiter `reconcile_open_week` aux utilisateurs dont les step snapshots ont changé depuis le dernier tick.

**C2 [C] High — 4 requêtes SQL par requête authentifiée.**
- `plugs/require_auth.ex:10` → `fetch_auth_user_from_access_token` (`accounts.ex:464`) → `Repo.get(User)` → `build_auth_user` → `auth_methods_for_user` (`:1246-1266`) = 3 `Repo.exists?` (email credential, google, apple). `GET /me` (`app_controller.ex:12`) rappelle `auth_user_for_id` → 8 requêtes.
- `authMethods` n'est consommé que par la page settings web et l'admin.
- Fix : le plug ne fait qu'un `Repo.get(User)` ; `authMethods` calculé paresseusement dans `/me`, login/refresh et admin ; `/me` réutilise `conn.assigns.auth_user`.

**C3 [C] High — Reconstruction PvP redondante.**
- `serialize_match/1` (`pvp.ex:774-781`) appelle `current_player_id_map` (`:927-941`) qui appelle `reconstruct_state/1` (`:562-583` : dernier snapshot + rejeu de tous les événements via `BattleEngine.simulate_action` ; snapshot seulement tous les 10 tours ou en fin de match, `:1147-1153`).
- `get_match`, `accept_match`, `perform_action`, `end_turn`, `get_spectate` reconstruisent donc **deux fois** ; `perform_action` rejoue l'événement qu'il vient d'écrire au lieu d'utiliser `new_state["currentPlayerId"]`.
- `list_spectatable` (`:530-540`) reconstruit **chaque match en cours du système** à chaque appel.
- Fix : persister `current_player_id` sur `pvp_matches` à l'append d'événement (comme `current_turn`), et passer l'état déjà calculé à `serialize_match`.

**C4 [C] High — Solveur Daily Numbers sur chaque GET.**
- `quests.ex:1855-1861` → `get_daily_numbers_puzzle` → `DailyNumbersSolutionHunt.get_or_create_puzzle` (`:27-67`) : `pg_advisory_xact_lock` puis, même quand le solution set existe, `generate_puzzle_at_attempt` qui appelle `solve/2` (`daily_numbers_engine.ex:54`, DP 2^n sur toutes les combinaisons). Les utilisateurs ayant terminé reprennent le même lock via `ensure_solution_set` (`quests.ex:1912`). Un slow-log à 150 ms existe déjà pour ce chemin (`quests.ex:41`).
- Tous les lecteurs d'un mode se sérialisent derrière le solveur des autres.
- Fix : cache `:persistent_term`/ETS du puzzle par `{date, mode, attempt}` ; ne prendre le lock que si le set manque ou si `solution_key_version` est périmé ; sauter `ensure_solution_set` quand le set est à jour.

**C5 [C] Medium — `Match.initial_state` chargé partout, historique non borné.**
- `pvp/match.ex:16` porte l'état d'ouverture complet ; aucune requête `Match` ne le projette hors. `list_history` (`pvp.ex:191-203`) charge **tous** les matchs terminés sans `limit` pour poser `hasReplayData` et `totalCount: length(...)`.
- Fix : `select` sans `initial_state` (ou `select_merge: %{has_replay: not is_nil(m.initial_state)}`), pagination + `Repo.aggregate(:count)`.

**C6 [C] Medium — Autres chargements non bornés.**
- `Social.list_giftable_users` (`social.ex:18-22`) charge tous les utilisateurs approuvés ; `gifts_for_user` (`:30-35`) charge tous les gifts avec 3 preloads.
- `Accounts.list_admin_users` (`accounts.ex:586-589`) charge tous les users ; `list_pending_access_requests` (`:688-704`) charge **tous les emails** dans un `MapSet` au lieu d'un `not exists`.
- `Quests` refait `Repo.get(User)` à répétition (41 sites via `current_reset_date_for_user` / `reset_timezone_for_user`, `quests.ex:120-129`) alors que `RequireAuth` l'a déjà chargé.
- Fix : `limit`/pagination, filtrage SQL, passer le `%User{}` déjà chargé.

**C7 [C] Medium — Le battle log grossit sans borne dans l'état.**
- `battle_engine.ex:4348` `Map.update!(state, "log", &(&1 ++ events))` (append O(n)) + ~15 `length(state["log"])`. `build_view/2` (`:4152-4157`) renvoie tout l'état, log inclus, à chaque `GET /pvp/matches/:id` et chaque action ; chaque snapshot le stocke aussi.
- Fix : prepend + longueur courante ; retirer/paginer `log` dans `build_view` (les clients reçoivent déjà `events` par action) ; route dédiée pour le log complet.

**C8 [C] Low-Medium — Ouverture de pack en boucle `get_by` + insert/update** (`inventory.ex:212-226`). Fix : grouper par `card_id` et `insert_all ... on_conflict: [inc: [quantity: ^n]]` (l'index unique existe).

**C9 [C] Low — Overhead par requête.**
- `website_document_plug.ex:178` : `File.read(index_path())` à chaque navigation HTML → cache `:persistent_term`.
- `raw_body_reader.ex:18` garde le body brut complet (jusqu'à 12 Mo) dans `conn.private` pour **toutes** les requêtes alors que seul `fitbit_controller.ex:120` le lit → scoper au webhook Fitbit.
- `media_controller.ex:46-66` proxifie chaque image (DB + MinIO + body en mémoire) sans ETag/304.

**C10 [C] Low — Projections live de classement recalculées par requête sans cache** (`leaderboards/query.ex:179-180`, `projection.ex:185-198`). Cache ETS court keyé `{board, period, max(updated_at)}`.

## 4. Web (`apps/web`) et packages

### 4.1 Bugs / incohérences

- **A1 [C] High — Déconnexion sur erreur transitoire de refresh.** `auth/session.ts:128-150` `restoreWebSession` : toute erreur non-401/403 (réseau, 5xx, **429**) appelle `clearLocalWebSession` → statut `anonymous` → `layout.tsx:168` redirige vers `/login`. Or `restore()` est appelé après **chaque mutation réussie** pour rafraîchir coins/dust (`core-pages.tsx:87,263,332,397,407`, `quest-pages.tsx:68`, `settings-page.tsx:63,70`) et frappe `POST /web/session/refresh`, limité à **20/min** (`config.exs:130`). Ouvrir/crafter/claim plus de 20 fois en une minute = 429 = logout. `refreshAccessTokenForApi` (`:152-165`) fait, lui, le bon choix (rethrow). Fix : ne vider la session que sur erreur d'auth ; remplacer `restore()` post-mutation par `webApiClient.me()` (déjà dans l'api-client, non utilisé par le web).
- **A2 [C] Medium — Cache react-query non vidé au logout** (`session.ts:167-177`) ; clés non scopées par user → après logout+login d'un autre compte dans le même onglet, les pages affichent les données du précédent pendant `staleTime`. Fix : `queryClient.clear()` dans `logout`.
- **A3 [C] Medium — POST à effet de bord utilisé comme `queryFn`** : `quest-pages.tsx:345-348` utilise `startDailyNumbersRanked` (POST `/ranked-start`) comme query avec `refetchOnWindowFocus` ; c'est le shim de compatibilité Phoenix (voir Phoenix A1). La clé `["daily-numbers","today",mode]` diffère de `["daily-numbers",mode]` (`:124`) → double fetch du même état. Fix : `dailyNumbersState(mode)` avec la clé existante.
- **A4 [P] Medium — Countdown Speed Calculus** (`quest-pages.tsx:412-427`) : deps incluent l'objet `finish` (nouvelle identité à chaque render) → timer recréé à chaque render ; après succès, `finish.mutate` peut re-tirer tant que `activeRun` n'est pas invalidé.
- **A5 [P] Medium — Timeout 8 s de l'`ApiClient` appliqué aux uploads** (`api-client/src/index.ts:316`, `upload()` `:398-408`) alors que l'UI promet 16 Mo (`catalog-pages.tsx:471`). Fix : timeout dédié pour `upload()`.
- **A6 [C] Low — Retry predicate incohérent** (`lib/api.ts:132-142`) : `WebApiError` 5xx retry, `ApiClientError` 5xx non.
- **A7 [C] Medium — `game-engine` contient un loader couplé à un ORM** (`combat/context.ts:37-105` `loadBattleContext(cardIds, drizzle: any)`), en contradiction avec la règle « pur » de CLAUDE.md ; 0 consommateur hors `apps/api` archivé. Supprimer.
